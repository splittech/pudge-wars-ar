# Ручная приёмка этапа 2

Реализация 2.1–2.12 готова к приёмке. Автоматическая проверка: 318/318 EditMode. Фактические сетевые замеры ещё не выполнены; этап остаётся открытым до заполнения этого списка и отчёта. Уже подтверждённые проверки можно учитывать, повторяя их при регрессии.

## Подключение и игра

- [ ] Запустить Boot: MPPM Host And Client, одинаковый протокол 9. На одном ПК IP — `127.0.0.1`; между устройствами — LAN IPv4 хоста. KCP — 7777, discovery — 47777.
- [ ] Create / Find / Join по IP, отмена подключения, недоступный адрес с таймаутом около 5 с, возврат в меню, повторный запуск и Training работают без зависших сцен/объектов.
- [ ] Два игрока минимум 5 минут ходят, меняют цели, бросают хуки, попадают и сталкивают хуки. HP/позиции/фазы совпадают; новых ошибок Console нет. Повторить с четырьмя игроками и при ограничении 20 FPS.
- [ ] Вход во время полёта хука показывает актуальное положение/фазу, без старта полёта заново. Локальные перенос/поворот/масштаб ArenaRoot не меняют серверную симуляцию.
- [ ] Ники обрезаются по краям, принимаются только длиной 2–16; регистронезависимый дубликат и пятый занятый/зарезервированный слот отклоняются до спавна. Разная версия протокола даёт понятный отказ.
- [ ] Discovery и подключение по IP работают на реальных Android-устройствах в одной Wi-Fi сети. MPPM не заменяет проверку broadcast между устройствами.

## Восстановление соединения

- [ ] Не нажимая Back, оборвать транспорт клиента (на Android выключить Wi-Fi на 10 с). Пока игрок отсутствует, герой остаётся уязвимым, активный хук продолжает полёт; новых команд движения нет.
- [ ] Сервер обнаруживает обрыв после KCP timeout (10 с), затем резервирует героя на 30 с. В пределах резерва Join с прежними IP/ником автоматически использует токен из RAM: тот же SessionPlayerId и netId, актуальные HP/позиция/хук, epoch увеличивается, второго героя/слота нет. При ReconnectInUse дождаться обнаружения старого обрыва и повторить Join.
- [ ] Повторить обрыв/возврат дважды. После истечения резерва старое восстановление отклоняется; последующий новый вход создаёт нового игрока. Чужой герой не захватывается.
- [ ] Явный Back освобождает слот сразу. Остановка хоста завершает сеанс; миграции хоста нет. Перезапуск приложения очищает RAM-токен.

## Prediction и плохая сеть

- [ ] На локальном HeroNet клиента сравнить Prediction Enabled on/off. Host не двигается с удвоенной скоростью. Проверить границы, быстрые смены цели, смерть, pull, reconnect: старые команды не продолжают движение после принудительного состояния.
- [ ] Локальный body/ring не борется с NetworkTransform: небольшие коррекции сглаживаются около 0.1 с, ошибка >1 единицы исправляется сразу. При RTT 0 подтвердить ошибку <=0.01 единицы после установления состояния.
- [ ] Проверить управляемость при RTT 150 мс / потерях 5%, включая хуки. После паузы кадра >1 с нет ускоренного проигрывания всей пропущенной симуляции.
- [ ] Выполнить матрицу prediction on/off × RTT 0/100/200 мс × потери 0/5% × отправка ввода 10/20/30 Гц (36 режимов). Отдельно сравнить частоты снимков 10/20/30 Гц при фиксированных остальных настройках. Серверная симуляция и prediction всегда 30 Гц. Частоту Mirror sendRate фиксировать и указывать в отчёте.

Настройка стенда: до Play добавить Mirror LatencySimulation на объект менеджера, в wrap указать существующий KcpTransport, в поле Transport менеджера — обёртку. На обеих сторонах задержка = половина желаемого RTT, jitter/scramble = 0, unreliable loss = требуемый процент. Ориентироваться на измеренный RTT; обёртка не моделирует потери reliable-канала. После лабораторной проверки вернуть обычный KCP.

## Измерения и завершение

- [ ] Для отклика несколько раз дождаться полной остановки героя и сглаживания, затем тапнуть в новую точку. Движение между уже движущимися целями не считается новым измерением отклика. Сравнить mean/p95 on/off; CSV измеряет CPU LateUpdate, аппаратную задержку экрана проверять отдельно при необходимости.
- [ ] Повторить нагрузочный замер на четырёх игроках MVP. Сохранить исходные CSV и companion `_input.csv`, сформировать [summary.md](summary.md), проверить полные повторы, сравнение режимов, mean/p95 и отсутствие пропусков обязательных сценариев.
- [ ] Подтвердить NFR-03: бюджет <20 000 B/s на отдельного клиента. Счётчик сообщений Mirror не включает весь транспортный overhead; для полного сетевого бюджета приложить измерение транспортного трафика с указанием источника. Host включает loopback: делить его суммарные байты на число игроков нельзя. UDP packets/наблюдаемые потери N/A не означают ноль.
- [ ] Записать устройства, сборки, настройки, результаты и обнаруженные проблемы рядом с отчётом. После успешной приёмки отметить соответствующие пункты этапа 2 в основном чек-листе.
