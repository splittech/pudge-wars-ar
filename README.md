# Pudge Wars AR

LAN-дуэль на хуках в AR для Android/ARCore. Unity 6000.6.5f1, URP.

Источники требований и архитектуры: [ТДД](Docs/pudge_wars_ar_tdd.md) и [чек-лист](Docs/pudge_wars_ar_checklist.md).

## Этап 0 — завершён

Добавлены шесть игровых конфигов с readonly-снимками данных, регистрации в ProjectScope, версия протокола 1, development-оверлей FPS/версии. Есть загрузка сцен, DI, экран загрузки, логирование и распознавание жестов. Обработана отмена переходов экрана загрузки; запущенные Unity-операции сцен завершаются до передачи отмены.

Ручные проверки этапа 0 подтверждены разработчиком; все пункты отмечены в чек-листе.

Оверлей: `Assets/Game/Prefabs/UI/Development Overlay.prefab`, экземпляр в Boot. В Prefab Mode можно менять оформление TMP и Canvas, а на DevelopmentOverlay — интервал обновления. FPS усредняется по unscaled-времени; оверлей работает в редакторе и development-сборках, в обычной сборке выключается.

Для проверки:

1. Открыть проект и запустить Play Mode из любой сцены: ожидается Boot → Main Menu.
2. Перейти кнопкой в Gameplay; проверить отсутствие ошибок, оверлей и логирование кликов/жестов.
3. В Android Build Profile включить Development Build, пройти XR Project Validation, собрать APK.
4. Установить APK на ARCore-совместимый телефон: проверить меню, FPS/версию и подключение Profiler.
5. После приёмки завершить чек-лист и зафиксировать результат коммитом. Git-теги не используются.

EditMode-тесты: через Test Runner открытого редактора либо при закрытом редакторе:

```text
unity test --mode EditMode
```

## Этап 1 — завершён

Запуск: Play Mode → Main Menu → Gameplay. Синий герой управляется игроком, оранжевый — манекен.

- Тап по столу перемещает героя; цель ограничивается своей половиной.
- Свайп от синего героя показывает прицел; отпускание бросает хук. Возврат пальца к герою отменяет бросок.
- Попадание снимает 175 HP и притягивает манекен; после возврата хука начинается перезарядка 3 с.
- Манекен автоматически восстанавливается через 2 с после попадания, когда хук уже вернулся. Reset training сбрасывает песочницу, Back to menu возвращает в меню.

Симуляция работает на 30 Гц, отображение интерполируется между тиками. Песочница активна в Editor и Development Build. После структурирования тестов: 101/101 EditMode-тест прошёл. Ввод также проверялся через виртуальный Touchscreen в Play Mode. Сеть, экономика, правила матча и AR-размещение ещё не подключены. Gizmos и настраиваемый лимит FPS реализованы; ручная приёмка подтверждена разработчиком, этап 1 завершён. FlatArenaAnchorProvider перенесён на этап 4 (AR).


Для проверки этапа 1: в Play Mode выбери ArenaRoot и включи Gizmos в Scene или Game view. На OfflineSimulationDriver флаг Draw Simulation Gizmos показывает границы и хитбоксы, Frame Rate Limit задаёт лимит FPS (например, 20). Значение 0 восстанавливает прежние FPS/VSync. Проверь движение, бросок, попадание, отмену свайпа и игнорирование касаний над UI. Симуляция всегда работает на 30 Гц. Результат этапа фиксируется коммитом после ручной приёмки; Git-теги не используются.


Стиль и структура тестов описаны в [правилах EditMode-тестов](Docs/pudge_wars_ar_tests.md): фабрики Setup, отдельные тестовые двойники, имена Method_Condition_ExpectedResult и блоки Arrange / Act / Assert.

## Этап 2 — сетевые переходы и DI-спавн (2.1–2.2)

В Boot добавлен Network Session с PudgeNetworkManager, KcpTransport (7777) и мостом к SceneService. Boot сохраняется, Menu/Gameplay загружаются аддитивно. Mirror возобновляет обработку сети после завершения загрузки и регистрации фабрики. Hero и MatchState создаются через VContainer под локальным ArenaRoot. Команды движения, серверная симуляция и сетевой бой пока не подключены.

Проверка в редакторе:

1. Выбрать MPPM-сценарий `Assets/Game/Configs/Development/Host And Client.asset` в Play Mode Scenarios и запустить его. Откроется главный и дополнительный редактор.
2. В главном редакторе после появления меню выбрать Network Session в Boot → инспектор PudgeNetworkManager → группа Session → Start Host.
3. В дополнительном редакторе задать Network Address = 127.0.0.1 → Start Client. На обоих экземплярах должны быть два статичных героя по разным берегам; кольцо отмечает локального героя. В Hierarchy под ArenaRoot — два Hero и один Match State.
4. Back клиента удаляет его героя на хосте; повторное подключение создаёт нового в свободном слоте. Back хоста или Stop Session возвращает оба экземпляра в меню.

Обычная кнопка перехода в Gameplay по-прежнему запускает офлайн-песочницу. Меню сетевого подключения добавляется в 2.7; восстановление того же героя — в 2.10. После проверки выбран обычный сценарий Default, поэтому простой Play Mode не запускает второй редактор автоматически.

Компиляция без ошибок, 112/112 EditMode-тестов. MPPM-проверка спавна, DI, владения, повторного подключения и очистки прошла. localhost дал KCP timeout, используйте 127.0.0.1. Серверная симуляция реализована в 2.3; следующий блок — 2.4, сетевые команды.

Проверка 06.11.2026: массовый сбой рендеринга URP в виртуальном редакторе обходится явным запуском основного редактора с `-force-d3d11`. На Unity 6000.6.5f1 с активной платформой Android проверены подключение клиента, два героя и корректное изображение Gameplay. Оба экземпляра используют Direct3D 11. Это параметр Windows-редактора; графический API Android-приложения он не меняет. Перед запуском команды закройте редактор, сохранив сцены:

```powershell
unity open C:/Dev/Unity/pudge-wars-ar --editor-version 6000.6.5f1 --build-target Android --args '-force-d3d11'
```

Уточнение 09.11.2026: D3D11 не устраняет все ошибки запуска MPPM. В клоне остаются сообщения для `AutodeskInteractive.shadergraph`, `TraceVirtualOffset.urtshader` и assert read-only AssetDatabase; принудительный переимпорт этих ассетов в основном редакторе не помог. Эти сообщения не скрываются.

Добавлен Editor-only обход SceneReference 5.0.0: в виртуальном проекте отключается только его внутренний обработчик входа в Play Mode, вызывающий `AssetDatabase.Refresh()` на read-only базе. Основной редактор продолжает генерировать карты сцен; клон использует подготовленные карты. Обход использует reflection к закреплённой версии пакета и требует проверки при её обновлении. Отмена fade-анимации загрузки проверяется в PlayerLoop без callback `Tween.Kill()` при уничтожении; остановка с активным tween после `DOTween.Clear(true)` прошла без прежнего исключения. Компиляция успешна, 112/112 EditMode-тестов прошли.

## Этап 2.3 — серверная симуляция

В сетевом GameplayScope зарегистрированы MatchSimulation, ServerTickRunner, MatchStateSink и ReconnectRegistry. Сервер считает игру на 30 Гц с максимумом четырёх шагов за кадр. После каждого шага sink записывает arena-позиции в localPosition героев, сохраняя визуальную высоту, и обновляет SyncVar HP/Alive/IsPulled/HookCooldownEnd. Офлайн-песочница сохранена.

При спавне герой получает состояние из конфигов и регистрируется в симуляции до AddPlayerForConnection. При обрыве снимается владение, останавливается самостоятельное движение, герой и слот сохраняются на 30 с; хук, притягивание и урон продолжают рассчитываться. По дедлайну объект удаляется и слот освобождается. Back/Stop Session клиента отправляет явный выход: сервер удаляет героя сразу и отключает соединение; при отсутствии ответа клиент завершает ожидание через 1 с. Остановка хоста очищает весь сеанс.

ProtocolVersion увеличен до 2 из-за новых полей HeroNet и LeaveSessionMessage. Сверка версий — 2.9, восстановление того же героя по токену — 2.10. Команды движения и броска добавляются в инкременте 2.4 ниже; синхронизация движения/HookNetState/RPC — 2.5. Отображение подключено в блоке 2.5 ниже.

Ручная приёмка Host + Client подтверждена разработчиком 10.11.2026. Проверяемые сценарии:

1. Запустить Host And Client, подключить клиент к 127.0.0.1. Проверить по два героя и одному MatchState; у HeroNet HP = 1000 и Alive = true.
2. Back клиента должен удалить его героя на сервере; повторный вход занимает свободный слот с новым SessionPlayerId.
3. Имитировать обрыв транспорта без Back: герой остаётся на хосте, слот занят; через 30 с герой удаляется. Повторное подключение до дедлайна пока создаёт другого героя в другом свободном слоте.
4. Stop Session хоста возвращает участников в меню. Обычный вход в Gameplay запускает прежнюю офлайн-песочницу.

Автоматическая проверка 09.11.2026: unity test --mode EditMode — 125/125 тестов, компиляция без ошибок. NUnit XML: test-results.xml. Пункт 2.3 завершён; следующий — 2.4 (сетевые команды).
## Начало 2.4 — сетевые команды

Локальный HeroNet реализует IPlayerCommands и отправляет move/throw через Mirror Command. Scoped LocalPlayerCommands связывает InputRouter с появившимся героем и снимает привязку при потере локального игрока. Сервер проверяет владельца, аутентификацию/готовность соединения, Alive/IsPulled, конечность координат, Idle/cooldown хука и частоту. Движение ограничивается своей половиной, направление броска нормализуется. В ближайший тик попадают последняя цель и один бросок, dt всегда задаёт сервер. При disconnect отложенный ввод очищается. Покупки пока отключены.

ProtocolVersion = 3. Сетевой Gameplay пока работает как боевая песочница без фаз матча (этап 3). RequestId/SessionEpoch и ответы о результате появятся в 2.6/2.9. Проверка 10.11.2026: 141/141 EditMode-тестов через unity test --mode EditMode, компиляция без ошибок. Ручная MPPM-приёмка ещё не проведена.

Ручная проверка базового ввода подтверждена разработчиком. Для регрессии: клиент управляет только своим героем, Back и обрыв очищают его отложенный ввод, обычный вход в Gameplay сохраняет офлайн-песочницу. Проверка сетевого отображения описана в 2.5 ниже.
## Начало 2.5 — синхронизация

Hero.prefab настроен через Unity Editor: NetworkTransformUnreliable отправляет только localPosition, ServerToClient; вращение и масштаб не синхронизируются. До появления predictor серверные снимки отображаются также для владельца. У клиента позиция героя теперь должна обновляться, поэтому свайп можно начинать возле его текущего отображения.

HookNetState передаёт фазу, origin/direction, timestamps, длину разворота и netId цели. Снимок обновляется при смене фазы/броска/цели. NetworkHookView вычисляет кончик по синхронизированному времени и рисует линию; движение хука не использует NetworkTransform. Возврат к движущемуся владельцу отображается приближённо; попадания и притягивание определяет сервер. HP доступно через R3 Health; урон даёт вспышку тела, RPC попадания/клэша — вспышку линии. ProtocolVersion = 4.

Ручная проверка 2.5 подтверждена разработчиком 10.11.2026. Сценарии регрессии: на Host + Client проверить движение обоих героев, свайп возле текущего положения на клиенте, вылет/возврат/попадание/притягивание, совпадение HP и вспышки. Проверить позднее подключение во время полёта, независимые позы ArenaRoot и очистку линий после выхода. Новый бросок пока ждёт серверного ответа; мгновенный косметический хук — 2.6. Из начальных точек расстояние между героями больше дальности хука, поэтому перед проверкой попадания нужно подойти ближе к реке.
Проверка 2.5: 154/154 EditMode-теста прошли через Unity Pipeline в открытом редакторе; компиляция без ошибок. Исправлены round-trip тест и явный формат HookNetState (41 байт). Результат — Temp/pipeline_test_status.json; test-results.xml выше относится к 2.4. Ручная проверка визуальной синхронизации подтверждена разработчиком 10.11.2026.

## Этап 2.6 — косметическое предсказание броска

Свайп локального игрока сразу создаёт голубой призрак хука. Сервер проверяет направление, владельца и RequestId/SessionEpoch, затем подтверждает бросок только после фактического шага симуляции. Снимок с теми же идентификаторами заменяет призрак золотым авторитетным хуком. Отказ удаляет призрак; при отсутствии результата/снимка ожидание заканчивается через 2 с в шкале NetworkTime. Призрак не наносит урон и не притягивает цель.

Принятый TargetActionResult сам по себе не убирает призрак до снимка. Поздние ответы и снимки старого запроса/эпохи не отменяют новый призрак. Потеря локального управления, смерть, притягивание и изменение эпохи сбрасывают ожидание. Счётчики запросов не оборачиваются. При reconnect в 2.10 потребуется увеличивать эпоху перед восстановлением управления.

ProtocolVersion = 5; HookNetState теперь 49 байт (добавлены RequestId и SessionEpoch). Покупки не подключены до этапа 3. Полный HUD и prediction движения относятся к следующим этапам.

Ручная приёмка 2.6 ещё не выполнена: на отдельном клиенте проверить немедленный голубой хук после свайпа и замену золотым, быстрые повторные свайпы, штатный отказ и очистку при выходе. При сетевой задержке эффект призрака заметнее; при низком RTT он может быть виден лишь один кадр. Отказ/тайм-аут/перестановка результата и снимка отдельно покрываются EditMode-тестами. Серверные попадания, HP и притягивание должны оставаться прежними.
Автоматическая проверка 2.6: 175/175 EditMode-тестов через Unity Pipeline; компиляция без ошибок. Результат — Temp/pipeline_test_status.json. Ручная приёмка 2.6 ещё не подтверждена.
