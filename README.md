# Pudge Wars AR

LAN-дуэль на хуках в AR для Android/ARCore. Unity 6000.6.5f1, URP.

Источники требований и архитектуры: [ТДД](Docs/pudge_wars_ar_tdd.md) и [чек-лист](Docs/pudge_wars_ar_checklist.md).

## Этап 0 — завершён

Добавлены шесть игровых конфигов с readonly-снимками данных, регистрации в ProjectScope, версия протокола 1, development-оверлей FPS/версии. Есть загрузка сцен, DI, экран загрузки, логирование и распознавание жестов. Обработана отмена переходов экрана загрузки; запущенные Unity-операции сцен завершаются до передачи отмены.

Ручные проверки этапа 0 подтверждены разработчиком; все пункты отмечены в чек-листе.

Оверлей: `Assets/Game/Prefabs/UI/Development Overlay.prefab`, экземпляр в Boot. В Prefab Mode можно менять оформление TMP и Canvas, а на DevelopmentOverlay — интервал обновления. FPS усредняется по unscaled-времени; оверлей работает в редакторе и development-сборках, в обычной сборке выключается.

Для проверки:

1. Открыть проект и запустить Play Mode из любой сцены: ожидается Boot → Main Menu.
2. Перейти кнопкой в Gameplay; проверить отсутствие ошибок, оверлей и логирование кликов/жестов.
3. В Android Build Profile включить Development Build, пройти XR Project Validation, собрать APK.
4. Установить APK на ARCore-совместимый телефон: проверить меню, FPS/версию и подключение Profiler.
5. После приёмки завершить чек-лист и зафиксировать результат коммитом. Git-теги не используются.

EditMode-тесты: через Test Runner открытого редактора либо при закрытом редакторе:

```text

```

## Этап 2.3 — серверная симуляция

В сетевом GameplayScope зарегистрированы MatchSimulation, ServerTickRunner, MatchStateSink и ReconnectRegistry. Сервер считает игру на 30 Гц с максимумом четырёх шагов за кадр. После каждого шага sink записывает arena-позиции в localPosition героев, сохраняя визуальную высоту, и обновляет SyncVar HP/Alive/IsPulled/HookCooldownEnd. Офлайн-песочница сохранена.

При спавне герой получает состояние из конфигов и регистрируется в симуляции до AddPlayerForConnection. При обрыве снимается владение, останавливается самостоятельное движение, герой и слот сохраняются на 30 с; хук, притягивание и урон продолжают рассчитываться. По дедлайну объект удаляется и слот освобождается. Back/Stop Session клиента отправляет явный выход: сервер удаляет героя сразу и отключает соединение; при отсутствии ответа клиент завершает ожидание через 1 с. Остановка хоста очищает весь сеанс.

ProtocolVersion увеличен до 2 из-за новых полей HeroNet и LeaveSessionMessage. Сверка версий — 2.9, восстановление того же героя по токену — 2.10. Команды движения и броска добавляются в инкременте 2.4 ниже; синхронизация движения/HookNetState/RPC — 2.5. Отображение подключено в блоке 2.5 ниже.

Ручная приёмка Host + Client подтверждена разработчиком 10.11.2026. Проверяемые сценарии:

1. Запустить Host And Client, подключить клиент к 127.0.0.1. Проверить по два героя и одному MatchState; у HeroNet HP = 1000 и Alive = true.
2. Back клиента должен удалить его героя на сервере; повторный вход занимает свободный слот с новым SessionPlayerId.
3. Имитировать обрыв транспорта без Back: герой остаётся на хосте, слот занят; через 30 с герой удаляется. Повторное подключение до дедлайна пока создаёт другого героя в другом свободном слоте.
4. Stop Session хоста возвращает участников в меню. Обычный вход в Gameplay запускает прежнюю офлайн-песочницу.

Автоматическая проверка 09.11.2026: unity test --mode EditMode — 125/125 тестов, компиляция без ошибок. NUnit XML: test-results.xml. Пункт 2.3 завершён; следующий — 2.4 (сетевые команды).

## Начало 2.5 — синхронизация

Hero.prefab настроен через Unity Editor: NetworkTransformUnreliable отправляет только localPosition, ServerToClient; вращение и масштаб не синхронизируются. До появления predictor серверные снимки отображаются также для владельца. У клиента позиция героя теперь должна обновляться, поэтому свайп можно начинать возле его текущего отображения.

HookNetState передаёт фазу, origin/direction, timestamps, длину разворота и netId цели. Снимок обновляется при смене фазы/броска/цели. NetworkHookView вычисляет кончик по синхронизированному времени и рисует линию; движение хука не использует NetworkTransform. Возврат к движущемуся владельцу отображается приближённо; попадания и притягивание определяет сервер. HP доступно через R3 Health; урон даёт вспышку тела, RPC попадания/клэша — вспышку линии. ProtocolVersion = 4.

## Этап 2.6 — косметическое предсказание броска

Свайп локального игрока сразу создаёт голубой призрак хука. Сервер проверяет направление, владельца и RequestId/SessionEpoch, затем подтверждает бросок только после фактического шага симуляции. Снимок с теми же идентификаторами заменяет призрак золотым авторитетным хуком. Отказ удаляет призрак; при отсутствии результата/снимка ожидание заканчивается через 2 с в шкале NetworkTime. Призрак не наносит урон и не притягивает цель.

Принятый TargetActionResult сам по себе не убирает призрак до снимка. Поздние ответы и снимки старого запроса/эпохи не отменяют новый призрак. Потеря локального управления, смерть, притягивание и изменение эпохи сбрасывают ожидание. Счётчики запросов не оборачиваются. При reconnect в 2.10 потребуется увеличивать эпоху перед восстановлением управления.

ProtocolVersion = 5; HookNetState теперь 49 байт (добавлены RequestId и SessionEpoch). Покупки не подключены до этапа 3. Полный HUD и prediction движения относятся к следующим этапам.

Ручная приёмка 2.6 подтверждена разработчиком 10.11.2026. Сценарии регрессии: на отдельном клиенте проверить немедленный голубой хук после свайпа и замену золотым, быстрые повторные свайпы, штатный отказ и очистку при выходе. При сетевой задержке эффект призрака заметнее; при низком RTT он может быть виден лишь один кадр. Отказ/тайм-аут/перестановка результата и снимка отдельно покрываются EditMode-тестами. Серверные попадания, HP и притягивание должны оставаться прежними.

## 2.7 — подключение через меню

Create game создаёт хост на KCP 7777 и рекламирует его через Mirror NetworkDiscovery (UDP 47777). Find LAN games запускает поиск в общей Wi-Fi-сети: найденные IPv4-хосты появляются кнопками Join <IP>. Один сервер показывается один раз по ServerId; без ответа запись исчезает через 10 с. Поиск идёт до Cancel или подключения. Если broadcast блокируется сетью, используйте Join by IP. На Android MulticastLock и разрешение CHANGE_WIFI_MULTICAST_STATE уже обеспечивает vendored Mirror.

Join by IP принимает IPv4; в MPPM на одном ПК используйте 127.0.0.1. localhost/DNS и IPv6 не принимаются. Соединение вместе с handshake ограничено 5 с, попытку можно отменить. С этапа 2.9 ProtocolVersion = 7; VersionAuthenticator сверяет версию до спавна. Поддерживающие handshake сборки с разными версиями получают сообщение Incompatible protocol с версиями клиента и хоста. Старые сборки без handshake завершаются по тайм-ауту.

После неожиданного обрыва установленного соединения сцена Gameplay выгружается и над Menu показывается Host disconnected. Return to menu подтверждает сообщение и разблокирует меню. Cancel, явный выход и отказ handshake этот экран не вызывают. Development Overlay в Editor/development-сборках показывает FPS, версию, роль offline/host/client/server и RTT в миллисекундах.

Проверено 12.11.2026: 212/212 EditMode-тестов и автоматические Play Mode-проверки аутентификации/спавна хоста, настоящего UDP Discovery в обе стороны, списка и подключения кнопкой, cancel, освобождения порта и экрана потери хоста. Подключение отдельного клиента через меню ранее подтверждено разработчиком. Ручная приёмка завершающего инкремента ожидается.

Для ручной проверки:

1. Host And Client: Create game в основном редакторе; Find LAN games → Join <IP> в дополнительном. При блокировке broadcast проверьте также 127.0.0.1 → Join by IP. Должны появиться два героя; движение/хуки продолжают работать.
2. Проверьте Cancel при поиске и при подключении, повторный поиск/вход и Training без сетевого сеанса.
3. Остановите хост при подключённом клиенте: клиент показывает Host disconnected, после Return to menu снова доступны создание/подключение. Явный выход клиента не должен показывать этот экран.
4. Проверьте несовместимые версии двух сборок с handshake: понятный отказ до появления героя. Проверьте роль и RTT в оверлее.
5. Два Android-устройства в одной Wi-Fi-сети: поиск, подключение из списка и по IPv4. При фильтрации broadcast/AP isolation в роутере поиск может быть недоступен; Windows-хосту нужны входящие UDP 47777 и 7777.

## 2.9 — ники и сетевые контракты

Перед Create game / Join укажите Nickname: после Trim нужно 2–16 UTF-16 символов, без управляющих символов. Ники уникальны без учёта регистра, включая зарезервированных после обрыва игроков. Начальное имя Player-xxxxxx генерируется отдельно на каждом запуске. Нормализованный ник сохраняется в контроллере при возврате в меню.

VersionAuthenticator сначала обменивается совместимым с версией 6 probe, затем AuthRequest/AuthResponse протокола 7. Ошибки версии, ника, занятого ника, заполненной сессии и reconnect-токена имеют явные коды и показываются в меню до спавна. Максимум 4 игровых/зарезервированных слота; Mirror допускает ещё короткие handshake-соединения, чтобы вернуть ServerFull. В MatchStateNet → Players синхронизируются SessionPlayerId, Nickname, Team, Ready, Connected; Ready остаётся false до лобби этапа 3. Токены в список не попадают.

После обрыва ник и герой сохраняются на 30 с; новое подключение с тем же ником без восстановления отклоняется. Явный Back/Cancel освобождает запись сразу. Восстановление владения и выдача/ротация токенов — 2.10; optional поле уже зафиксировано, но в 2.9 любой переданный токен получает InvalidReconnectToken.

PlayerInfo, HookNetState, MovementFrame и MovementSnapshot имеют явные readers/writers. Формат, размеры и ограничения приведены в ТДД 12.8; MovementFrame/Snapshot пока только DTO для 2.11. Покупки пока не меняют экономику и отвечают адресным отказом; RequestId/SessionEpoch и ActionKind разделяют ответы покупки и броска.

Ручная проверка 2.9:

1. В MPPM создайте хост с ником ` Alice `; у клиента попробуйте `ALICE` — должен быть понятный отказ, без второго героя и без экрана потери хоста.
2. Подключитесь как `Bob`: на обоих экземплярах MatchStateNet → Players содержит Alice и Bob с разными ID и Connected=true. Проверьте обычные движение/хуки.
3. Явно выйдите клиентом: Bob сразу исчезает из списка и может войти снова. При обрыве транспорта запись Bob остаётся с Connected=false, Ready=false и удерживает имя/слот до 30 с.
4. Пустой/однобуквенный/слишком длинный ник должен отклоняться. При четырёх занятых или зарезервированных слотах новый ник получает Game is full.
5. Если есть сборка с протоколом 6, проверьте отказ несовместимой версии в обоих направлениях.

Проверено автоматически 12.11.2026: 283/283 EditMode-теста, компиляция без ошибок; MPPM — Alice/ALICE/Bob, одинаковый состав на хосте и клиенте, явный выход и реальный обрыв с резервом ника. Реализация 2.9 готова к дополнительной ручной приёмке; следующий функциональный блок — 2.10.

## 2.10 — повторное подключение

Текущая версия протокола — 8. После неожиданного обрыва клиент получает экран потери соединения: Return to menu → повторный Join by IP к тому же хосту с прежним ником. IP сохраняется в поле. Токен автоматически отправляется из памяти Boot; до 30 с после обнаружения обрыва сервер возвращает того же героя с текущими HP/позицией/хуком. Токен и SessionEpoch меняются, дубликат героя не создаётся.

Если прежнее соединение ещё активно на сервере, будет предложение подождать timeout и повторить: токен сохранён. KCP обнаруживает молчащий транспорт примерно через 10 с; затем начинается резерв 30 с. Истёкший/чужой токен получает отказ и удаляется на клиенте; следующий Join — новый игрок. Явный Back/Stop/Cancel подключённого клиента освобождает героя сразу. Остановка хоста завершает сессию, миграции нет. После перезапуска приложения RAM-токен потерян.

Отложенная ручная приёмка:

1. Host And Client: подключить клиента, записать его SessionPlayerId/netId/HP/позицию и epoch. Инициировать неожиданный обрыв, сохранив запущенный хост. На сервере герой остаётся, Connected=false, готовность снята, движение остановлено, активный хук и урон продолжаются.
2. До 30 с повторить Join к тому же IP с прежним ником. Проверить те же ID/netId/состояние, одного героя и увеличенную epoch; управление должно снова работать.
3. Повторить обрыв и возврат; прежний токен не должен допускать второго владельца. После резерва >30 с — понятный отказ, затем новый вход с новым ID.
4. Проверить явный Back: немедленное освобождение слота. Остановить хост: сеанс завершается, восстановить старый сеанс невозможно.
5. На Android отключить Wi-Fi на 10 с и вернуть; при ReconnectInUse подождать timeout и повторить. Позднее перепроверить HP/золото/улучшения/KD/респавн после этапа 3 и AR-привязку после этапа 4.

Проверка реализации 2.10: 290/290 EditMode-тестов в batch mode, компиляция без ошибок, отчёт `test-results.xml`. Интерактивный редактор не открывался; ручная приёмка MPPM/Android отложена.

## 2.11 — prediction и reconciliation движения

Текущий протокол — 9. Клиент создаёт кадры движения 30 Гц независимо от прихода снимков; сервер выполняет свою симуляцию 30 Гц и подтверждает последовательность адресными снимками. Локальное движение не ждёт RTT. История — 120 тиков, replay идёт только после ServerTick; старая epoch/повторный снимок игнорируются, неизвестная история вызывает resync. Смерть/pull останавливают предсказание и очищают старую цель. Host повторно не симулируется.

В Play Mode выберите своего HeroNet на клиенте: Prediction Enabled включает/выключает локальный отклик. Movement Send Rate (10/20/30) регулирует частоту отправки пачек, серверные/клиентские тики всегда 30 Гц. Movement Snapshot Rate задаётся на соответствующем HeroNet на хосте независимо от send rate. Перед стартом хоста можно отдельно менять Mirror sendRate для лабораторного сравнения. В обычном запуске все частоты по умолчанию 30.

Оверлей: Pred ON/OFF/HOST, err в единицах арены (зелёный <=0.1, красный >0.1), c/s — коррекции/сек, h — история, ack/t — подтверждение и ServerTick, send/snap — фактические пакеты ввода/снимки в секунду. Малые визуальные коррекции сглаживаются 0.1 с, большие и принудительное состояние применяются сразу. Сетевой корень продолжает получать NetworkTransform; смещение локальных body/ring отделено от серверных координат и боевых столкновений.

Проверено: 308/308 EditMode-тестов в batch mode, без ошибок компиляции. Ручная приёмка отложена: Host And Client, prediction on/off, RTT 0/100/200 ms, потери 0/5%, send/snapshot rates 10/20/30; проверить движение, смену цели, смерть/pull, повторный вход, отсутствие второго движения host. Количественные показатели задержки/ошибки и сетевой отчёт пока не измерены.
